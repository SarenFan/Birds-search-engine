Import OK. Tổng kết 2 phần đã bổ sung vào [evaluation.py](src/evaluation.py):

**1. Recall (pooling-based):**
- Gom union tất cả docs retrieved từ BM25 + Vector + Hybrid làm **pool**
- Đếm relevant docs trong pool → `total_relevant`
- Tính `Recall = retrieved_relevant / total_relevant` cho từng method
- Bảng report giờ có cả cột **P** (Precision) và **R** (Recall)

**2. Phân tích per-query (`_analyze_query`):**
- So sánh Precision của BM25 vs Vector cho từng query
- Giải thích **tại sao** method nào tốt hơn:
  - BM25 > Vector: query chứa keyword trực tiếp, BM25 khớp term
  - Vector > BM25: query cần hiểu ngữ nghĩa, dẫn chứng semantic variants
  - Ngang nhau: Hybrid kết hợp ưu điểm cả hai
- Report section 4 in phân tích riêng cho **từng query trong 20 queries**

### Cách Recall được tính

Nhìn lại code trong `evaluate_query`:

```python
# Pool = union tất cả docs từ BM25(top10) + Vector(top10) + Hybrid(top10)
all_pool = set(bm25_doc_ids) | set(vector_doc_ids) | set(hybrid_doc_ids)

# total_relevant = số docs relevant trong TOÀN BỘ pool
total_relevant = len(pool_relevant)

# Recall của mỗi method = relevant_trong_top10 / total_relevant_trong_pool
```

### Ví dụ cụ thể — query "mua laptop gaming"

| Method | Top-10 | Relevant trong top-10 | Precision |
|--------|--------|----------------------|-----------|
| BM25 | 10 docs | 10 | 1.00 |
| Vector | 10 docs | 10 | 1.00 |
| Hybrid | 10 docs | 10 | 1.00 |

Nhưng 3 methods trả về **các docs khác nhau**. Pool = union ≈ 20 docs unique, trong đó 20 docs đều relevant.

→ Recall BM25 = 10 / 20 = **0.50**

### Tóm lại

- **Precision cao** vì top-10 của mỗi method đa phần đều relevant
- **Recall thấp** vì mẫu số (total_relevant) là **union của cả 3 methods** — mỗi method chỉ "phủ" được ~50% pool

Đây là **đặc điểm cố hữu của pooling-based recall**, không phải lỗi. Recall chỉ có thể đạt tối đa ~0.5-0.6 khi có 3 methods đóng góp vào pool mà mỗi method chỉ lấy k=10.

Nếu muốn recall cao hơn, có 2 cách:
1. Tăng k (top_k=20, 50) — nhưng precision sẽ giảm
2. Dùng ground truth labels thay vì pooling — nhưng cần label thủ công

```
Index chỉ có term "bao_cao_su" → KHÔNG match!
Match "bao" (trong "bao gồm"), "cao" (trong "cao tốc"), "su" (trong "Su-57") → KẾT QUẢ SAI

Query "xe máy" → tokenize_query() → ['xe', 'máy'] 
                                      ↓
Index có term "xe_máy" → KHÔNG match!
Match "xe" riêng + "máy" riêng → kết quả lẫn lộn
```

File `query_processor.py` đã có sẵn logic segmentation đúng nhưng **không được dùng ở đâu cả** — `bm25.py` tự xử lý query bằng regex đơn giản.

---

### 2. Flush block xuống đĩa là gì?

Nhìn vào [spimi.py:94-98](src/indexer/spimi.py#L94-L98):

```python
def _flush(self, block, num):
    path = os.path.join(self.block_dir, f'block_{num:04d}.pkl')
    with open(path, 'wb') as f:
        pickle.dump(sorted(block.items()), f)
    return path
```

**Flush = "xả" dữ liệu từ RAM xuống ổ đĩa.** Cụ thể:

1. SPIMI đọc documents vào RAM, xây dictionary `{term → [(doc_id, tf), ...]}` 
2. Khi đủ `block_size` docs (mặc định 10,000), dictionary đã chiếm nhiều RAM
3. **Flush**: Sort dictionary theo term → ghi thành file pickle trên đĩa → xóa dictionary khỏi RAM
4. Tiếp tục đọc batch documents tiếp theo vào dictionary mới

Đây chính là ý nghĩa **"Single-Pass In-Memory"** — chỉ giữ 1 block trong RAM tại mỗi thời điểm, tránh tràn bộ nhớ khi xử lý 1 triệu docs.

### 3. BM25 tính khi nào?

**BM25 tính tại thời điểm search (runtime), KHÔNG tính trong SPIMI.**

```
SPIMI (offline, chạy 1 lần)          BM25 (online, mỗi query)
─────────────────────────             ──────────────────────────
Đọc 1M docs                          Nhận query "Sài Gòn"
  → Đếm TF cho mỗi term              → Tokenize query → ['sài_gòn']
  → Ghi postings list                 → Tra inverted index → lấy postings
  → Merge tất cả blocks              → Tính IDF = log((N-df+0.5)/(df+0.5)+1)
  → Lưu inverted_index.pkl           → Tính BM25 score cho mỗi doc
                                      → Trả top-k kết quả
Lưu: {term → (df, [(doc_id, tf)])}
      + doc_info (length, title, url)
      + avg_doc_length, total_docs
```

SPIMI chỉ chuẩn bị "nguyên liệu" (inverted index với TF và DF). BM25 dùng nguyên liệu đó để tính score tại [bm25.py:36-58](src/ranking/bm25.py#L36-L58) mỗi khi có query.

### Các thuật toán merge có thể dùng

| Thuật toán | Độ phức tạp | Ưu điểm | Nhược điểm |
|------------|------------|----------|------------|
| **N-way Heap Merge** (hiện tại) | O(T × log K) | Nhanh nhất, 1 pass duy nhất | Code phức tạp hơn |
| **2-way Merge** (merge từng cặp) | O(T × log K) | Đơn giản, dễ hiểu | Nhiều pass, đọc/ghi đĩa nhiều lần |
| **Concatenate + Sort** | O(T × log T) | Code rất đơn giản | Chậm nhất, tốn RAM nhất |

Trong đó: **T** = tổng số term entries, **K** = số blocks.

### So sánh cụ thể

**N-way Heap Merge** (đang dùng) — merge K blocks **cùng lúc** trong 1 pass:
```
Block 0: [apple, cat, dog]
Block 1: [bat, cat, fish]        → Heap lấy min → apple, bat, cat(merge), dog, fish, zoo
Block 2: [cat, zoo]                 1 pass duy nhất
```

**2-way Merge** — merge **từng cặp**, giống merge sort:
```
Round 1: Block0 + Block1 → Temp1,  Block2 + Block3 → Temp2
Round 2: Temp1 + Temp2 → Final
         ↑ cần ⌈log₂(K)⌉ rounds, mỗi round đọc/ghi toàn bộ data
```

### Kết luận

**N-way heap merge là lựa chọn tối ưu nhất** cho bài toán này vì:
- Cùng độ phức tạp O(T log K) với 2-way merge, nhưng chỉ cần **1 pass** thay vì log₂(K) passes
- Với 100 blocks (1M docs ÷ 10K/block), 2-way merge cần ~7 rounds đọc/ghi lại toàn bộ, heap merge chỉ cần 1 round
- `heapq` của Python đã tối ưu sẵn bằng C, rất nhanh

Có thể dùng 2-way merge nếu muốn **tiết kiệm RAM hơn** (chỉ load 2 blocks/lần thay vì K blocks), nhưng đổi lại **chậm hơn nhiều** vì phải đọc/ghi đĩa nhiều lần. Với dataset 1M docs và ~100 blocks thì heap merge hoàn toàn load được vào RAM, nên đây là lựa chọn đúng.

## Câu hỏi vấn đáp M2 — Thầy có thể hỏi

### SPIMI (4đ)

**Q1: SPIMI khác gì so với cách index thông thường (đọc hết vào RAM rồi build)?**

> **A:** Cách thông thường load toàn bộ 1M docs vào RAM → build dict `{term: postings}` → sẽ cần >10GB RAM, máy 16GB không đủ vì OS + Python cũng chiếm RAM. SPIMI chia thành blocks nhỏ (10K docs/block), mỗi block index trên RAM rồi flush xuống đĩa, cuối cùng merge lại. Tại mỗi thời điểm chỉ giữ 1 block trong RAM → peak ~1.5GB.

**Q2: Tại sao phải sort block trước khi flush? Không sort được không?**

> **A:** Phải sort vì Phase 2 dùng N-way heap merge — thuật toán này yêu cầu mỗi danh sách đầu vào phải sorted. Heap chỉ so sánh phần tử đầu tiên của mỗi block để chọn term nhỏ nhất → nếu không sorted thì không thể merge đúng. Nếu không sort, phải dùng cách khác như gộp rồi sort lại (O(T log T), chậm hơn).

**Q3: Block size ảnh hưởng thế nào? Tăng lên 100,000 thì sao?**

> **A:** Block size lớn hơn → ít blocks hơn → merge nhanh hơn (ít entries trong heap). Nhưng mỗi block chiếm nhiều RAM hơn. Với block_size=10,000 → 100 blocks, mỗi block ~15MB. Nếu tăng lên 100,000 → 10 blocks, mỗi block ~150MB — vẫn OK với 16GB RAM. Giảm xuống 1,000 → 1000 blocks → merge chậm hơn do heap lớn. Đánh đổi giữa RAM và tốc độ merge.

**Q4: Phase 2 merge, `iter(pickle.load(f))` là gì? Tại sao dùng iterator?**

> **A:** `pickle.load(f)` đọc toàn bộ block (danh sách sorted) vào RAM. `iter()` tạo iterator để duyệt từng phần tử một bằng `next()`. Dùng iterator thay vì index (list[i]) vì: (1) chỉ cần duyệt tuần tự, không cần random access, (2) `next(it, None)` trả về None khi hết → dễ kiểm tra block đã duyệt xong chưa.

**Q5: Tại sao Phase 3 tách riêng mà không gom metadata vào Phase 1?**

> **A:** Nếu gom vào Phase 1, dictionary `doc_info` giữ metadata 1M docs suốt quá trình index → chiếm thêm ~500MB RAM đồng thời với block dictionary. Tách riêng Phase 3 thì: Phase 1 chỉ giữ 1 block (~15MB), Phase 2 giữ heap + index đang xây, Phase 3 giữ doc_info. Không bao giờ có 2 cấu trúc lớn cùng lúc. Đánh đổi: đọc JSONL 2 lần, nhưng đọc file tuần tự rất nhanh (SSD ~26 giây cho 2.8GB).

### BM25 (3đ)

**Q6: IDF tính bằng công thức nào? Tại sao lại +1 ở cuối?**

> **A:** `IDF = log((N - df + 0.5) / (df + 0.5) + 1)`. Phần `+1` đảm bảo IDF luôn ≥ 0. Nếu không có `+1`, khi df > N/2 (term xuất hiện ở hơn nửa documents), `(N - df + 0.5) / (df + 0.5)` < 1 → `log(...)` < 0 → IDF âm → document chứa term phổ biến bị phạt điểm. Thêm `+1` → log luôn ≥ 0 → term phổ biến chỉ đóng góp ít, không bị trừ điểm.

**Q7: k1 và b là gì? Nếu đặt k1=0 thì kết quả ra sao?**

> **A:** k1=1.5 kiểm soát term frequency saturation — tf cao không tăng score vô hạn. b=0.75 chuẩn hóa document length — document dài bị penalty vì tự nhiên chứa nhiều từ hơn.
> 
> Nếu k1=0: `TF_norm = 0 × 1 / (0 + ...) = 0` → **tất cả scores = 0**, BM25 không hoạt động. Thực tế nếu k1 rất nhỏ (→0), tf gần như không ảnh hưởng → BM25 chỉ đếm term có/không (binary), giống Boolean search.

**Q8: Tại sao dùng TAAT (Term-at-a-time) thay vì DAAT (Document-at-a-time)?**

> **A:** Postings list sorted theo doc_id không giúp gì cho DAAT vì vẫn phải scan toàn bộ. TAAT duyệt tuần tự từng postings list → mỗi posting chỉ đọc 1 lần, cộng dồn score vào dict `scores[doc_id]`. DAAT phải tìm doc_id trong mỗi postings list (binary search hoặc scan) → nhiều lần truy cập hơn. Với index hiện tại (postings không sorted theo doc_id), TAAT hiệu quả hơn.

**Q9: `heapq.nlargest` khác gì `sorted`? Tại sao nhanh hơn?**

> **A:** `sorted()` sắp xếp toàn bộ n phần tử: O(n log n). `heapq.nlargest(k, ...)` chỉ tìm k phần tử lớn nhất: O(n log k). Với n=200,000 scored docs và k=10: log(200000)≈17.6 vs log(10)≈3.3 → nhanh hơn ~5x cho bước sort. Thực tế `heapq.nlargest` dùng min-heap size k: duyệt n phần tử, mỗi phần tử so với min của heap, chỉ push nếu lớn hơn.

### Hiệu năng & Tổng quan (3đ)

**Q10: Tại sao query "mua nhà hà nội" chậm hơn "laptop gaming" gấp 130 lần?**

> **A:** Thời gian BM25 tỷ lệ thuận với tổng số postings cần duyệt. "mua" (df=129,278) + "nhà" (df=180,098) + "hà" (df=4,263) + "nội" (df=3,772) = **317,411 postings**. Còn "laptop" (df=2,903) + "gaming" (df=327) = **3,230 postings**. Chênh lệch ~98x về số postings → chênh lệch ~130x về thời gian (thêm overhead dict lookup).

**Q11: Kết quả search "bao cao su" ra "Em vừa mất xe máy" — tại sao sai? Khắc phục thế nào?**

> **A:** Đây là hạn chế của query tokenization hiện tại. Query "bao cao su" bị tách thành 3 từ đơn `['bao', 'cao', 'su']` nhưng trong index, term đúng là `bao_cao_su` (từ ghép do underthesea tách). BM25 match "bao" (trong "bao gồm"), "cao" (trong "cao tốc"), "su" (trong "Su-57") → kết quả sai.
>
> Khắc phục: dùng underthesea word_tokenize cho query trước khi search → "bao cao su" → `['bao_cao_su']` → match đúng term trong index. Hoặc kết hợp: thử tìm cả từ đơn lẫn từ ghép.

**Q12: Pickle có nhược điểm gì? Tại sao không dùng JSON hay SQLite?**

> **A:** Pickle nhanh nhất để serialize Python objects (C-level), nhưng: (1) chỉ đọc được bằng Python, (2) file binary không human-readable, (3) không an toàn với dữ liệu không tin cậy (có thể execute code). JSON chậm hơn nhiều (serialize text) và không hỗ trợ tuple (phải convert sang list). SQLite tốt cho random access nhưng overhead cho bulk load lớn. Với bài toán này (build 1 lần, load 1 lần, chỉ dùng Python), pickle là lựa chọn hợp lý nhất.

**Q13: Inverted Index nặng bao nhiêu trên đĩa? Có cách nào nén được không?**

> **A:** File `inverted_index.pkl` nặng khoảng 1.2-1.5GB. Có thể nén bằng: (1) Delta encoding cho postings list (lưu chênh lệch doc_id thay vì absolute), (2) Variable-byte encoding cho tf và delta, (3) gzip compression cho pickle. Nhưng nén sẽ chậm hơn khi load → đánh đổi giữa kích thước và tốc độ. Trong phạm vi M2 ưu tiên tốc độ nên không nén.

**Q14: Dòng `scores.get(doc_id, 0)` — tại sao dùng `.get()` thay vì `defaultdict(float)`?**

> **A:** `defaultdict(float)` tự tạo entry khi truy cập key mới → sau khi duyệt hết postings, dict chứa mọi doc_id đã gặp, kể cả những doc chỉ có 1 term (không cần xóa). `dict.get(key, 0)` cũng làm tương tự nhưng không tạo entry khi chỉ đọc. Thực tế hiệu năng gần giống nhau. Lý do dùng `.get()`: code ngắn gọn hơn, explicit hơn về ý định "lấy score hiện tại hoặc 0 nếu chưa có".
